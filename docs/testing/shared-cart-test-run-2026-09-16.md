## 2. 结果

### 共享语义

| 用例 | 结果 | 观察 |
|---|---|---|
| **CART-RT-01** | PASS | 两人扫同一张桌码 → **同一个购物车**，但**各自独立的 participant token 与 id** |
| CART-RT-02 | PASS | A 加菜，B 立刻读到（1 行，总额 8.00） |
| CART-RT-02b | PASS | B 再加 2 份，A 读到总额 24.00 —— 双向可见 |

### 并发写

| 用例 | 结果 | 观察 |
|---|---|---|
| **CART-RT-06** | PASS | 两人**同一瞬间**各加 1 份：两次都 200，数量增量**精确等于 2**。在三张空桌上各跑一次，**三次都是 2**，没有丢写 |
| **CART-RT-08** | PASS | A 删除某一行、B 同时改这一行的数量 → **删除 200、更新 404**，购物车剩 0 行，**没有幽灵行存活** |
| **CART-RT-09** | PASS | A 清空、B 同时加菜 → 两人读到的最终状态**完全相同**，收敛一致 |
| **CART-RT-10** | PASS | **两人同时点结账 → 都返回 200，且拿到同一个 orderId，只创建了一个订单** |

## 3. 一处夹具返工

`CART-RT-06` 第一次报 FAIL：期望数量 2，实得 5。不是丢写或重复写——
`seat()` 加入的是**这张桌上已存在的购物车**，里面还留着同一脚本前面测试加的 3 份。
两次并发写都成功了，一份都没丢。

改为测**增量**而非绝对值，并换到三张空桌各跑一次，三次增量都精确是 2。

> 这是今天第四次断言错配。前三次分别是：`/api/order/guest` 用空列表表示无权、
> 菜品改价缺版本号被 400、写餐厅配置用错字段名（那次改坏了生产）。
> 共同点是**前置状态或前置操作没有先确认**。对并发测试尤其要注意：
> **测增量，不要测绝对值**，因为共享夹具的初始状态未必是你以为的那个。
